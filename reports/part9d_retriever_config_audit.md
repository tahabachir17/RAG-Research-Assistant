# Part 9d — Retriever Configuration Audit

Date: 2026-08-13

## Finding

The Part 9c scores were produced by **hybrid dense + sparse retrieval followed
by cross-encoder reranking**. They were not produced by BM25-only retrieval and
did not silently degrade to sparse-only. The configured outer wrapper was
`_MMRRetriever`, but MMR was deliberately bypassed at the run's top-k 4 cutoff;
therefore the effective scoring path was hybrid + reranker.

## Construction and call trace

1. `evaluation/run_part9c_retrieval_scores.py:135-140` defaults
   `retrieval_config` to `hybrid_rerank_mmr`.
2. The script calls `build_benchmark_retriever(args)` once, then calls that
   object's `search(..., top_k=4)` for every one of the 75 questions
   (`run_part9c_retrieval_scores.py:25-30`).
3. `evaluation/run_full_ragas_eval.py:143-243` constructs this chain:
   `_MMRRetriever` → `_RerankingRetriever` → `HybridRetriever` →
   (`DenseRetriever`, `SparseRetriever`), plus `CrossEncoderReranker`.
4. `_RerankingRetriever.search` requests 20 fused candidates and sends them to
   the cross-encoder (`run_full_ragas_eval.py:93-97`).
5. `HybridRetriever.search` invokes both `dense_retriever.search` and
   `sparse_retriever.search` before RRF fusion
   (`retrieval/hybrid_retriever.py:39-66`).
6. `_MMRRetriever.search` returns reranked candidates unchanged when top-k is
   below 20 (`run_full_ragas_eval.py:106-110`). Thus MMR was configured but not
   applied at k=4.

## Runtime evidence

The local benchmark collection `bench_external_chunks` existed at audit time
with **2,777 points**. The builder's preflight checks collection existence and a
positive point count before loading retrieval models; a missing or empty
collection raises `RuntimeError` rather than selecting sparse retrieval
(`run_full_ragas_eval.py:113-140, 153-158`). Sparse-only is possible only through
the explicit `--retrieval-config sparse` branch.

A dependency-level counter trace over three representative Part 9c questions
recorded:

| Component | Calls | Result |
| --- | ---: | --- |
| Dense Qdrant search | 3 | Non-empty on all three |
| Sparse BM25 search | 3 | Non-empty on all three |
| Cross-encoder rerank | 3 | Four `source=reranked` results per query |
| MMR sample | 0 | Correctly bypassed because k=4 < 20 |

An additional direct trace on `qasa-1511.04587-13` returned 20 dense results,
20 sparse results, 20 hybrid candidates, and four final reranked results. The
first dense chunk ID was `b89983af-9857-55cb-a3c4-2695b5d284d4`.

The saved Part 9c artifact independently records `config=hybrid_rerank_mmr`,
`candidate_k=20`, `top_k=4`, and `mmr_applied_at_top_k=false` in
`evaluation/data/eval_results/part9c_retrieval_20260813/retrieval_scores.json`.
All 75 rows were generated by the same retriever instance; the run completed
without a recorded dense/hybrid failure or exception.

## Conclusion

There was **no silent BM25 fallback** in Part 9c. The low scores—especially the
QASPER Hit@4 of 0.20—are genuine candidate-ranking/top-four retrieval results
from the hybrid + reranker path. The next diagnosis should therefore focus on
where reviewed evidence ranks before and after reranking, not on Qdrant
availability.
